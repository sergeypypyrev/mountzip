# ZipContent

Дерево каталогов ZIP-архива в компактном виде, для файловой системы поверх
архива. Одни и те же исходники собираются для user space и для модуля ядра
Linux. Архив читается библиотекой [zipr](../zipr).

## Структура

```c
enum ElementType { ElementFile = 0, ElementDirectory = 1 };

struct Element {			/* 16 байт */
	union {
		uint64_t position;	/* файл: позиция в центральном каталоге */
		struct {
			uint32_t first;	/* каталог: индекс первого ребёнка */
			uint32_t count;	/* и их число */
		} directory;
	};
	uint32_t nameOffset;		/* смещение имени в пуле */
	uint16_t nameLength;
	uint8_t type;			/* enum ElementType */
};

struct ZipContent {
	struct Element *elements;	/* elements[0] — корень */
	uint32_t elementCount, directoryCount, fileCount;
	char *names;			/* пул имён, без завершающих нулей */
	uint32_t namesSize;
	uint64_t skipped, duplicates;
};
```

- Дети каталога лежат подряд и отсортированы по имени побайтно, как
  `memcmp`. Поиск имени — двоичный поиск, `readdir` — проход по диапазону
  `elements[first, first + count)`.
- В пуле хранится только последний компонент пути: для
  `spot/ZRX/ETH/2022-12-31/23` это `23`.
- По `position` функция `ziprEntryAt()` читает запись архива: размер,
  смещение данных, CRC, полное имя. Её же передают в `ziprFopen()`.
- Индекс элемента подходит для номера inode (например, `index + 1`).

## API

```c
struct ZipContent content;
const struct Element *e, *child;
struct Zipr *zip;
uint32_t i;

ziprOpen("/path/a.zip", &zip);
zipContentBuild(&content, zip);                 /* построить дерево */

zipContentFind(&content, "dir/sub", 7, &e);     /* путь от корня */
zipContentLookup(&content, e, "name", 4, &e);   /* одно имя в каталоге */

child = zipContentChildren(&content, e);        /* readdir */
for (i = 0; i < e->directory.count; i++)
	use(zipContentName(&content, &child[i]), child[i].nameLength,
	    zipContentIsDirectory(&child[i]));

zipContentIndex(&content, e);                   /* номер для inode */
ziprEntryAt(zip, e->position, &entry, buf, sizeof(buf));   /* файл */

zipContentDestroy(&content);
ziprClose(zip);
```

Все функции возвращают `0` или отрицательный errno. Ошибки поиска:
`-ENOENT` (нет имени) и `-ENOTDIR` (компонент пути — файл, или путь
заканчивается на `/`, а найден файл). Подробности — в
[zipContent.h](zipContent.h).

После построения дерево только читается: его можно использовать из любого
числа потоков без блокировок.

## Как строится дерево

Имена в архиве — это просто строки. ZipContent приводит их к дереву по
таким правилам:

- **Пустые компоненты и `.` выбрасываются.** `/a//./b` превращается в
  `a/b`.
- **Записи с `..` в пути или с нулевым байтом в имени пропускаются.** Это
  защита от выхода за точку монтирования. Счётчик — `skipped`.
- **Каталоги создаются.** Если в архиве есть только `a/b.txt`, каталог `a`
  всё равно появится. Запись каталога `a/` необязательна.
- **Одинаковые пути.** Каталог побеждает файл с тем же именем, а из
  нескольких файлов остаётся последний в центральном каталоге, как при
  распаковке с перезаписью. Скрытые записи считаются в `duplicates`.

Алгоритм:

1. **Чтение каталога.** zipr читает центральный каталог потоком. Каждый
   компонент пути становится элементом, индекс родителя пишется в
   отдельный массив. Каталоги находятся через хеш-таблицу по паре
   (родитель, имя). Файлы в таблицу не попадают, поэтому она маленькая:
   405 тыс. каталогов на 9,7 млн файлов. Каталог предыдущей записи
   запоминается: файлы одного каталога обычно идут подряд, и для них хеш
   не считается.
2. **Группировка по родителю.** Считается число детей каждого каталога,
   каждому каталогу выдаётся диапазон индексов, элементы переставляются на
   свои места без второй копии массива.
3. **Сортировка** каждого диапазона по имени: `qsort_r` в user space,
   `sort_r` в ядре.
4. **Удаление дубликатов**: одинаковые имена после сортировки оказываются
   рядом.

Сложность — O(n) плюс сортировка внутри каталогов. Массивы заранее
выделяются по числу записей из EOCD (с ограничением сверху через размер
центрального каталога, если число записей в архиве неверное) и в конце
урезаются до точного размера.

## Память и скорость

`/dev/shm/2022.zip`, 6,1 ГБ, 9,68 млн файлов (`zipContentTool s`):

| | |
|---|---|
| элементов | 10 081 472 (405 400 каталогов, 9 676 072 файла) |
| элементы: 16 Б × 10,08 млн | 161,3 МБ |
| пул имён | 23,4 МБ |
| **итого после построения** | **184,7 МБ** |
| пик во время построения (RSS процесса) | 261 МБ |
| время построения (каталог в page cache) | 1,3 с |

Сверх итоговых 185 МБ во время построения нужны массив родителей
(4 Б на элемент), хеш-таблица каталогов, массив счётчиков при группировке и
запас в пуле имён до финальной урезки.

Ограничения: до 2³² − 1 элементов и 4 ГиБ имён (32-битные поля). В ядре
одна аллокация ограничена `INT_MAX` (лимит `kvmalloc`), то есть массив
элементов вмещает около 134 млн элементов. При превышении возвращается
`-EFBIG`.

В ядре `zipContentBuild` вызывает `cond_resched()` и прерывается с
`-EINTR` по фатальному сигналу.

## Сборка и тесты (user space)

zipr ожидается в `./zipr`. В этом дереве это символическая ссылка на
`../zipr`, путь можно поменять: `make ZIPR=/path/to/zipr`.

```sh
make            # build/libzipContent.a (ZipContent + zipr) и build/zipContentTool
make test       # ~10 с
```

```sh
build/zipContentTool l a.zip              # все пути, в глубину, по порядку
build/zipContentTool s a.zip              # статистика, память, время
build/zipContentTool d a.zip [DIR]        # дети каталога
build/zipContentTool f a.zip PATH...      # найти пути
```

Тесты (`tests/test.py`) создают архивы и сравнивают результат утилиты с
моделью этих правил на Python. Проверяются полный список путей,
статистика, содержимое каталогов, поиск (для файлов ещё и то, что
`position` указывает на последнюю запись с этим путём) и ошибки поиска.
Архивы:

- пустой, из одного файла, обычный с записями каталогов;
- с трудными именами: `..`, `.`, `//`, ведущий `/`, нулевой байт,
  дубликаты, файл и каталог с одним именем, UTF-8 и невалидный UTF-8,
  компонент в 3000 байт, глубина 200;
- 3000 случайных путей с повторами;
- 70 000 файлов в одном каталоге с переполненным счётчиком в EOCD (массивы
  растут в процессе);
- 5000 каталогов (хеш-таблица растёт);
- чередующиеся каталоги (кеш предыдущего каталога не помогает);
- архив, созданный модулем `zipfile` из Python.

Каждый архив проверяется в обычной сборке и в сборке с ASan и UBSan. Затем
500 случайно испорченных архивов прогоняются через сборку с санитайзерами:
ошибки допустимы, падения и срабатывания санитайзеров — нет.

## Модуль ядра

Как в zipr, библиотека компонуется в ваш модуль. В [Kbuild](Kbuild)
собирается демонстрационный модуль:

```sh
make kmod
sudo insmod zipContentDemo.ko zip=/dev/shm/2022.zip find=spot/ZRX/ETH/2022-12-31/23
dmesg | tail
sudo rmmod zipContentDemo
```

Он строит дерево, выводит число каталогов и файлов, память и время
построения, первые имена корня и результат поиска.

Для своего модуля в Kbuild:

```make
mymod-y := main.o zipContent/zipContent.o zipr/zipr.o
ccflags-y := -I$(src)/zipr -I$(src)/zipContent
```
