# zipr

Небольшая библиотека на C для чтения ZIP-архивов. Одни и те же исходники
собираются для user space и для модуля ядра Linux. Рассчитана на большие
архивы: десятки гигабайт и десятки миллионов файлов.

| | user space | ядро |
|---|---|---|
| stored (0) | да | да |
| deflate (8) | нет (`-EOPNOTSUPP`) | да, через `zlib_inflate` |
| ввод-вывод | `open`/`pread` | `filp_open`/`kernel_read` |
| память | `malloc` | `kvmalloc` |
| CRC-32 | slice-by-8, ~1,6 ГБ/с | `crc32_le` |
| сортировка индекса | `qsort` | `sort` (на месте) |

Поддерживаются ZIP64 (архивы и файлы больше 4 ГиБ, больше 65535 записей),
данные перед архивом (например, SFX-заглушка) и комментарий архива.
Архивы без ZIP64 с больше чем 65535 записями, у которых счётчик в EOCD
переполнен, тоже читаются. Не поддерживаются многотомные архивы, шифрование
и сочетание ZIP64 с данными перед архивом.

## Большие архивы

Память не зависит от размера архива и числа записей:

- `ziprOpen()` читает только записи в конце файла (EOCD, ZIP64 EOCD) и
  работает одинаково быстро для любого архива.
- Центральный каталог (для 10 млн записей это ~700 МБ) в памяти не
  хранится. Итератор читает его потоком через буфер 256 КиБ и проверяет
  каждую запись при разборе.
- Данные файлов читаются по требованию, порциями размера буфера
  вызывающего.

Единственная структура, которая растёт с архивом, — необязательный индекс
имён `ziprIndex()`: 12 байт на запись (32-битный хеш имени и позиция в
каталоге, отсортированные по хешу). С ним `ziprFind()` — это двоичный
поиск и одно чтение записи с диска. Без него — проход по всему каталогу.

Замеры на этой машине (`make test-big`, NVMe, каталог в page cache):

| Операция | Время | Пик памяти |
|---|---|---|
| прочитать файл 12 ГиБ с проверкой CRC | 7,7 с | 0,6 МБ |
| открыть файл со смещением больше 4 ГиБ | 0,00 с | 0,6 МБ |
| перебрать 10 млн записей | 0,14 с | 0,6 МБ |
| найти имя без индекса (последнее в каталоге) | 0,16 с | 0,6 МБ |
| построить индекс на 10 млн записей и найти 3 имени | 2,0 с | 219 МБ |

Сам индекс на 10 млн записей занимает 115 МБ. Остальное — временный буфер
`qsort` из glibc на время сортировки слиянием. В ядре `sort()` работает на
месте, и пик будет около 115 МБ. Время сортировки в ядре я не измерял. Это
heapsort, он медленнее glibc и, скорее всего, займёт несколько секунд.

С холодным кешем перебор упирается в чтение каталога с диска.

## API

```c
struct Zipr *z;
struct ZiprIter *it;
struct ZiprEntry e;
struct ZiprFile *f;
char buf[4096];
ssize_t n;
int ret;

ziprOpen("/path/a.zip", &z);              /* открыть архив */

ziprIterOpen(z, &it);                    /* перебрать имена */
while ((ret = ziprNext(it, &e)) > 0)
	printf("%.*s\n", (int)e.nameLen, e.name);
ziprIterClose(it);                       /* ret < 0: каталог повреждён */

ziprIndex(z);                             /* необязательно: быстрый поиск */
ziprFind(z, "dir/file.txt", 12, &e);      /* найти по имени */

ziprFopen(z, &e, &f);                     /* открыть файл в архиве */
while ((n = ziprFread(f, buf, sizeof(buf))) > 0)
	use(buf, n);                       /* распаковать по частям */
ziprFclose(f);                            /* закрыть файл */

ziprClose(z);                             /* закрыть архив */
```

Подробности — в комментариях в [zipr.h](zipr.h). Главное:

- Все функции возвращают `0` или отрицательный errno, `ziprNext` — `1`
  (есть запись) или `0` (конец), `ziprFread` — число байт.
- **Время жизни имени.** `e.name` не завершается нулём, длина — в
  `e.nameLen`. После `ziprNext` указатель живёт до следующего вызова на
  том же итераторе. После `ziprFind` указывает на переданную строку. После
  `ziprEntryAt` — на буфер вызывающего.
- **Запись можно запомнить без имени.** В `struct ZiprEntry` есть всё, что
  нужно `ziprFopen` (смещение, размеры, CRC, метод). Есть ещё `e.pos` —
  позиция в каталоге: по ней `ziprEntryAt()` перечитает запись вместе с
  именем. Для ФС это значит, что в inode достаточно хранить эти поля, а
  имена 10 млн файлов в памяти держать не нужно.
- `ziprCount` возвращает число записей из EOCD. Для архивов без ZIP64 с
  больше чем 65535 записями оно взято по модулю 65536. После `ziprIndex`
  число точное.
- `ziprCentralDirectorySize` возвращает размер центрального каталога.
  Запись в нём занимает не меньше 46 байт, так что размер даёт верхнюю
  оценку числа записей, даже если `ziprCount` неточен.
- `ziprFread` возвращает меньше запрошенного только в конце файла. CRC
  проверяется на вызове, который отдаёт последний байт: вместо данных он
  вернёт `-EBADMSG`. Ошибки запоминаются.
- В ядре буфер `ziprFread` — память ядра. `copy_to_user` делает
  вызывающий код.

### Потоки

Архив после открытия только читается. Разные потоки могут одновременно
работать каждый со своим итератором и своими открытыми файлами. Нельзя:
вызывать `ziprIndex` параллельно с чем-либо на том же архиве (вызовите его
один раз сразу после открытия) и использовать один итератор или файл из
двух потоков.

### Ядро

Все функции могут спать, вызывать их можно только в контексте процесса.
`ziprIndex` для больших архивов работает секунды. Он вызывает
`cond_resched()` и прерывается с `-EINTR`, если процесс получает фатальный
сигнал: смонтировать огромный архив можно отменить через Ctrl-C.

Самая большая аллокация ограничена `INT_MAX` (лимит `kvmalloc`), то есть
индекс вмещает до ~178 млн записей. Для большего числа вернётся `-EFBIG`.

## Что важно для ФС поверх архива

- Каталоги в ZIP — это просто префиксы путей, записи каталогов может и не
  быть. Список файлов каталога (`readdir`) из индекса по хешам не получить.
  ФС должна построить своё дерево (например, при монтировании, одним
  проходом итератора) и хранить в узлах `e.pos` или поля для `ziprFopen`.
- Чтение deflate-файла с произвольного смещения требует распаковки с
  начала: zipr читает файлы только последовательно. Для `read()` из
  середины большого deflate-файла понадобятся точки восстановления
  (сохранённое окно 32 КиБ каждые N мегабайт). Для stored-файлов
  произвольный доступ тривиален, но в API пока не вынесен.

## Сборка и тесты (user space)

```sh
make            # build/libzipr.a и build/ziprTool
make test       # основные тесты, ~15 с
make test-big   # большие архивы, ~30 с, ~1 ГБ на диске (build/big/)
```

`ziprTool` — утилита для проверки:

```sh
build/ziprTool l a.zip              # список
build/ziprTool n a.zip              # подсчитать записи перебором
build/ziprTool t a.zip              # прочитать все файлы, проверить CRC
build/ziprTool x a.zip name         # файл в stdout
build/ziprTool f a.zip name...      # найти имена
build/ziprTool -i x a.zip name      # то же, но через индекс
build/ziprTool -b 7 x a.zip name    # читать по 7 байт
```

`make test` собирает ещё два варианта с ASan и UBSan. Один из них с
`-DZIPR_TEST_ZLIB`: он включает deflate через системную zlib. Этот флаг
нужен только для тестов: так в user space проверяется тот же код
распаковки, что работает в ядре. Тесты создают архивы через Python и
проверяют:

- содержимое при размерах буфера 1, 7, 4096 и 65536;
- поиск с индексом и без, `ziprEntryAt` для найденных записей;
- записи больше буфера итератора: имена до 65527 байт и комментарии по
  65535 байт;
- комментарий с поддельной подписью EOCD, данные перед архивом;
- ZIP64: 70000 записей, архив с полем Zip64 extra, собранный вручную, и
  архив без ZIP64 на 70000 записей с переполненным счётчиком;
- порчу CRC и deflate, обрезанный архив, не-ZIP, каталог вместо файла;
- 600 случайно испорченных архивов (перебор, чтение, поиск по индексу):
  ошибки допустимы, срабатывания санитайзеров — нет.

`make test-big` создаёт разреженный архив с файлом 12 ГиБ, за которым идёт
файл со смещением больше 4 ГиБ, и архив на 10 млн записей (каталог
690 МБ). Он проверяет результаты и выводит время и пик памяти. Число
записей и размер можно поменять: `BIG_ENTRIES=...`, `BIG_GIB=...`.
`BIG_REGEN=1` пересоздаёт архив на 10 млн записей.

## Модуль ядра

Библиотека не отдельный модуль: `zipr.c` компонуется в ваш модуль, как в
[Kbuild](Kbuild). Демонстрационный модуль выводит первые записи архива в
dmesg, читает эти файлы с проверкой CRC и по желанию ищет имя через индекс:

```sh
make kmod                         # ziprDemo.ko для текущего ядра
make kmod KDIR=~/src/linux-6.12   # для другого
sudo insmod ziprDemo.ko zip=/root/a.zip list=20 find=dir/name.txt
dmesg | tail
sudo rmmod ziprDemo
```

Нужны `CONFIG_ZLIB_INFLATE` и `CONFIG_CRC32`, в ядрах Debian обе включены.

Если библиотеку понадобится вынести в отдельный модуль для нескольких
других, добавьте `EXPORT_SYMBOL_GPL` к функциям из `zipr.h`.

## Лицензия

Двойная лицензия `GPL-2.0 OR BSD-2-Clause` на выбор пользователя, для всех
файлов, включая демонстрационный модуль. Тексты лицензий лежат в
[LICENSES/](LICENSES/), сводка — в [LICENSE](LICENSE).

Модуль ядра, в который компонуется `zipr.c`, должен объявить лицензию,
совместимую с GPL: `MODULE_LICENSE("Dual BSD/GPL")`, как в демонстрационном
модуле, или `MODULE_LICENSE("GPL")`. Строку `"BSD"` ядро не принимает: модуль
с ней помечает ядро как tainted и не видит символов `EXPORT_SYMBOL_GPL`.
